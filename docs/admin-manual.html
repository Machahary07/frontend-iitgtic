00  How to read this book

Part One is orientation — signing in, the shape of the console, and the order to work in on a normal day. Part Two is the reference: one chapter per screen, each with what it is for, what every button does, and the mistakes worth avoiding. Part Three is the ledger of what has been built and tested. Part Four is for whoever keeps the lights on.

The status marks

Every feature in this book carries one of three marks. They mean exactly this and nothing softer:

Done Built, working on the live site, and exercised end to end.
In progress Working, but something outside the code is still missing.
Not doing Considered and rejected on purpose, with the reason given.

A “Not doing” is not a gap. It is a decision, and the reason is recorded so nobody re-opens it by accident.

01  Getting in

There is one sign-in door for the whole site. What you see after it depends on what your account is, not on which address you typed.

1.1The one door

Everyone — TIC staff, founders, and the people founders add to their startups — signs in at /login. The server reads your account’s role and opens the matching console: admins land in /tic-admin, founders in /founder. You never need to remember a second address.

  1. Go to iitgtic.itsjeu.com/login.
  2. Enter your email and password. Complete the bot check if it appears — it is Cloudflare Turnstile and usually passes without a click.
  3. You arrive on the Overview screen. The sidebar on the left is the whole console.

1.2Your session

Signing in issues a signed, httpOnly session cookie that lasts eight hours. It cannot be read by anything running in the page, and it is tied to you personally — every change you make in the console is recorded against your name, not against “the system”.

Sign out from the menu in the top-right of any console screen. Closing the tab does not sign you out; the eight hours do.

1.3The very first admin

On a brand-new installation there are no accounts at all, so there is nobody to sign in as. /tic-admin/login exists for exactly that one moment: it offers a setup form, takes the bootstrap password from the server’s environment, and creates the first admin. After that it stops granting access forever, and every further admin is created from Users → + New admin (§9).

If the setup form appears and admins already exist

The environment is wrong, not the database. That screen is chosen by counting admin accounts, so anything that stops the count — a key from the wrong Supabase project, a typo in the project URL, an unreachable host — used to look identical to a fresh install. The console now names the actual failure and refuses to bootstrap while it cannot read the table. Do not try to “set it up again”. Call the maintainers (§20).

1.4Who is who

RoleWhat it isCreated by
AdminTIC team. Sees everything, decides everything, every action audited.Another admin, in Users
FounderRuns one or more startups. Registers them, applies for incubation, posts roles, adds team members — nothing of which is public until an admin approves it.Self, at /apply
Team memberSomeone a founder added to their startup. Waits in the Approvals queue before it can do anything.A founder, approved by an admin
VisitorNo account. Reads the public site and can apply to one advertised role without signing up.—

Founders and their team members sign themselves up. Only admin accounts are created inside the console.

2.2Conventions you will meet everywhere

The screen never blanks

Every section is rendered by the server before it is sent, so moving between sections keeps the current screen on show until the next one is ready. If a screen looks stuck, it is loading, not broken.

Toasts confirm, they do not ask

A short message slides in at the corner after every action — green for done, red for refused. If no toast appears, the action did not run.

Anything destructive asks first

Deletes and take-downs open a proper dialog that traps focus and closes on Esc. There are no browser confirm() pop-ups anywhere in the console. Read the sentence in the dialog — it names exactly what is about to go.

A refusal needs a reason

Anywhere you send something back to a founder, the reason box is not optional. The founder reads that sentence in their own console, and a refusal they cannot read is a dead end for both of you.

Private documents are never public links

Resumes, pitch decks, CVs and financials live in private buckets. The console hands out a link that expires after ten minutes. Reload the page for a fresh one; never paste one into an email.

2.3A suggested daily round

  1. Overview. Read the tiles. Anything with a number on it is work waiting.
  2. Approvals. Clear it. Nothing a founder writes is public until you do, so this queue is the one that holds the site up.
  3. Role applicants → the new tab. Shortlist, send on, or decline. Each decision emails the applicant.
  4. Applications → the New tab. Open, read, move to under review or decide.
  5. Email. Glance at the usage meter and the failed tab. A run of failures means something is wrong upstream.
  6. Activity, weekly. Skim what changed and who changed it.

04  Approvals

Nothing a founder writes reaches the public site until it is approved here. Four queues share one screen, and the screen is empty when there is nothing to decide.

4.1The four queues

QueueWhat is waitingYour two buttons
New startupsA founder registered a company. Shows the contact person, email, phone, website and the date it was registered.Verify · Refuse
Job postingsA role written by a startup. Read expands the sector, the full description and the apply link before you decide.Approve · Send back
Team membersSomebody a founder added to their startup. Until approved, that person can sign in but can do nothing.Approve · Send back
Company detail changesAn edit to a verified startup’s own details — name, website, contact person, contact email, phone — shown as a before-and-after per field.Approve · Send back

4.2Working the queue

  1. Read the entry. On a job posting, press Read first — approving a description you have not read is how a bad role reaches the board.
  2. To accept, press the primary button. The change is live on the public site immediately and the founder is told.
  3. To refuse, type the reason in the box first, then press the red button. The console will stop you and say so if the box is empty.
The unverified-company flag

A job posting from a startup that is not yet verified carries a line saying so. Approving that role does not put it on the board — the startup itself has to be verified first. Deal with the startup in the New startups queue, or in Companies (§5), and the role appears.

Why a reason is compulsory

The founder reads your sentence in their own console, beside the thing that came back. “Send back” with no reason produces a founder who resubmits the same thing. One line — “the description names a salary we cannot advertise” — closes the loop.

Done  All four queues live, decisions audited, refusal reasons reaching the founder console.

05  Companies

The register of every startup account. Approvals (§4) is the inbox; this is the permanent record, and the place to change a decision you have already made.

5.1The table

Columns: Company, Contact, Website, Status, Signed up, Actions. A refused company keeps the reason on the row so nobody has to go hunting for why.

Statuses

StatusMeans
pendingRegistered, waiting on TIC. Invisible on the public site; cannot post roles.
verifiedCleared. Its approved roles appear on the Opportunities board and it can read its own applicants.
rejectedRefused, with the reason recorded and sent to the founder.

5.2The actions

ButtonWhat happens
ApproveMoves the startup to verified. Its approved roles go live. A “company verified” email goes out.
RejectOpens a reason box, then moves it to rejected. A “not verified” email goes out carrying your reason.
RevertPuts a decided company back to pending. Use this when you decided too early. It sends nothing — returning a record to its opening state is an internal correction, not news for the founder.
DeleteRemoves the account for good. Asks first. This is not a way to hide a company from the board — refuse it instead.
Delete is not the same as reject

Reject keeps the record, the reason, and the audit trail, and the founder is told. Delete removes the account. Reach for reject in almost every case; keep delete for duplicates, tests and accounts created in error.

Done  Verify, refuse, revert and delete all live, each one audited and each one emailing the right message.

06  Incubation applications

The eight-step, 38-question application a founder fills in per startup, with four document uploads. This is where it is read and decided.

6.1The queue

Five tabs, each carrying its own count: New · Under review · Accepted · Rejected · All. The table shows the startup, the founder, when it was submitted, its status, and — on anything decided — the note that went with the decision.

From the row you can Review (open it in full), Accept, or Reject. Accepting or rejecting from the row is for the obvious cases; anything you have not read should be opened.

6.2Reading one in full

Review opens the whole application: every answer, grouped as the founder filled it in, and the four documents — pitch deck, founder CV, financials, incorporation certificate.

The document links expire

Each document has an Open button that signs a fresh link good for ten minutes. If a link has gone stale, reload the page. A document that was never uploaded reads File missing rather than a dead button.

6.3Deciding

The review panel has two text boxes and three buttons.

Message to applicant
Goes into the email the founder receives. Write it as if they will read only this sentence, because they will.
Internal note
Stays in the console. For the team, never sent.
Accept
Moves to accepted and sends the acceptance email.
Mark under review
Signals the team has it in hand. Sends the “under review” email.
Reject
Moves to rejected and sends the decline, carrying your message.
Delete application
Removes the record and its uploaded documents. Asks first.
Deleting takes the documents with it

These are somebody’s financials and identity documents. Deleting the application removes the files from storage first, on purpose — but it is irreversible, and the record of the application goes with it. Reject rather than delete unless the entry is a duplicate or a test.

Done  Queue, full review, signed document links, three-way decision and delete, all audited and each state emailing the founder.

07  Posted jobs

7.1Two kinds of role

TabWhere it comes fromCan you take it down?
TIC jobsThe centre’s own openings, seeded in the site’s contentEdit them in Content (§11)
Startup jobsWritten by a verified startup in its own console and approved by TICYes — take down from here

Columns: Role, Company, Type, Sector, Source, Posted, Approval.

7.2Taking a role down

Deleting a company-posted role removes it from the public board. It does not delete the people who already applied to it — their applications keep a snapshot of the role and company name, so the Role applicants screen still reads correctly after the posting is gone.

An edit re-queues a live role

When a startup edits a role that is already public, it goes back into Approvals (§4) and comes off the board until it is approved again. That is intended: an approved description is what was approved, not whatever it was later changed into.

Done

08  Role applicants

People who applied to an advertised role. Applying needs no account, so this is the one queue where the person on the other end has no console to check — every decision here is communicated by email, and only by email.

8.1The pipeline

StatusMeansEmail sent
newJust arrived. Nobody has looked.“Application received”, on submit
shortlistedWorth taking further.“Shortlisted”
forwardedSent on to the company that posted the role.“Sent to the company”
rejectedNot taken forward.“Not taken forward”

The tabs mirror those states. A per-role dropdown — Every role by default — narrows the table to one posting.

8.2What you can do

Open application
The full record: contact details, every answer, and a signed link to the resume good for ten minutes.
Shortlist
Moves to shortlisted and emails the applicant.
Sent on
Moves to forwarded and emails the applicant. Use it when the company has actually been given the application.
Decline
Moves to rejected and emails the applicant.
Export CSV
Downloads what is currently in view — every role, or the one selected in the dropdown. The file is date-stamped.
Each button sends a real email to a real person

There is no draft state here. Pressing Decline tells somebody they did not get the job. Check you are on the right row — the table is sorted by date, and rows move as you filter.

8.3Resumes and retention

Resumes sit in a private bucket, one folder per role. Nothing about them is public. Deleting an applicant removes the file first and the row second, so no resume is left orphaned in storage. A console action can also clear a whole role at once, resumes first, for when a posting is finished with.

There is deliberately no automatic purge

A scheduled deletion of people’s documents is only ever noticed after it has already run. Clearing is a decision somebody makes, on a role, on purpose.

8.4What the startup sees

A verified startup reads the applicants for its own roles at /founder/applicants — contact details, answers, signed resume links and its own CSV export. It cannot see your review notes, and it has no way to change a status. Triage stays with TIC.

Done  Queue, tabs, filter, export, three-way triage, signed resume links, safe deletion, applicant emails at every step.

09  Users

Every account on the system, whatever kind. This is the only screen that can create an admin.

9.1The tabs

All · Admins · Founders · Never signed in · Suspended. “Never signed in” is the useful one: an account created but never used is usually a typo in an email address.

Columns: Account, Role, Last signed in, Joined, Actions. Two badges may appear beside the role — suspended and unconfirmed (the person never clicked the link in their confirmation email).

9.2What you can do

Change role
The dropdown on the row. Promoting somebody to admin gives them everything in this book.
Suspend
Blocks sign-in without deleting anything. Reversible with Restore. This is the right first move for a compromised or disputed account.
Delete
Removes the account. Asks first. Irreversible.
+ New admin
Name, email, and a temporary password you choose. They sign in with it at /login and change it themselves afterwards.
You cannot act on yourself

Your own row has no buttons and its role dropdown is disabled. It is not possible to suspend, delete or demote yourself out of the console by accident.

Hand the temporary password over out of band

It is shown once, in plain text, on the screen that creates the account. Send it by a channel the person already controls — not in the same email as their address, and not in a shared inbox.

Done  Roles, suspend/restore, delete, admin creation, self-protection.

10  Activity

Two things on one screen: what changed in the data, and what people looked at on the site.

10.1The audit log

One entry per change to a company, a job, an application or a profile, showing who, what, when, and — expanded — a Field / Before / After table for every value that moved.

The log is written by the database, not by the console

It is written by Postgres triggers, so a row changed through any route — the console, a script, the SQL editor — is recorded the same way. It is not possible to make a change that the console then declines to log. This is why the log is worth trusting in a dispute.

An admin action names the person who took it, not “the system”. The How this log works panel on the screen restates this in one paragraph for anyone reading over your shoulder.

10.2Page impressions

A card per public page over All, 30 days or 7 days, with three numbers: total impressions, unique human visitors, and bot hits. Crawlers are separated out by user agent rather than being quietly counted as people, so the human figure is the one to quote.

Recent visits beneath it is the raw tail — the last page views as they arrived.

Admin traffic is flagged, not hidden

Views of console pages are recorded and attributed to the signed-in admin. They are marked as such, so your own clicking around does not inflate a public page’s numbers.

Done  Trigger-written audit with before/after diffs; impressions with bot separation over three ranges.

11  Content

Every word and every image on the public site is edited here. No developer, no deploy, no waiting.

11.1How it works

The site is built from a set of named sections — one per page or per block of a page. The index screen lists them; opening one gives you an editor built from the shape of that section’s own data. Text fields are inputs, long copy is a textarea, lists can be reordered and added to, and nested groups open into their own sub-forms.

The consequence worth knowing: a new field becomes editable the moment it exists. Nobody has to build an admin screen for it.

11.2Editing a section

  1. Open the section from the Content index.
  2. Edit the fields. Nothing is written while you type — the editor works on a copy.
  3. Press Save changes. The button reads Saved when there is nothing outstanding, so an unsaved edit is visible at a glance.
  4. The public site is showing it immediately. Open the page in another tab to check.

Reset to default copy throws your edits away and restores the text the site shipped with. It asks first.

11.3Images

Any field that is an image — a photo, a logo, an avatar, an icon — renders as a preview with an Upload image button and a box to paste a URL into instead. Uploads go to the public site-assets bucket and the URL is saved into the section.

ConstraintValue
Maximum size5 MB per image
AcceptedImages only — the bucket refuses anything else
Who can uploadAdmins only. There is no other write path into that bucket.

People cards — team, governing body, mentors — each carry an avatar. A card shows the photograph when one is set and keeps a plain circle when it is not, so the pages read correctly before the photography arrives.

11.4Two things editing content also changes

  • Search snippets. A page’s meta description is read from its own opening copy, so rewriting the introduction rewrites what Google shows.
  • The audit trail. Every save records a before and an after in Activity (§10), so a change can be read back — and undone by hand — later.
The site cannot be taken down by a bad save

A section that has never been saved, or a database that cannot be reached, falls back to the copy bundled with the site. The worst a bad edit does is show the wrong words on one section until it is fixed or reset.

Done  Schema-driven editor, image upload per field, audited saves, per-section reset. In progress  The real photography, logos and startup marks — placeholders in several places today.

12  Email

Everything the system has ever tried to send, whether it arrived, how much of the monthly allowance is left, and who can no longer be written to.

12.1The meters

Across the top: the plan in use, this month’s and today’s sends against their caps, delivered all time, and a last 30 days trend. The allowance is counted from the log itself, and the same check runs before every send — a message that would exceed the cap is recorded as blocked rather than being thrown at the provider to fail.

12.2The delivery log

One row per attempt, with the recipient, template, subject and time. Tabs: All · Sent · Failed · Blocked, and a switch to include test sends, which are hidden by default.

StatusMeansWhat to do
sentAccepted by the provider, with a message id.Nothing. Delivery feedback arrives separately.
failedRejected, or the request never completed.One is noise. A run of them is a real fault — call §20.
blockedNever attempted: no API key, the template is switched off, the allowance is spent, or the address is suppressed.Read which. The reason is the fix.

Opening a row shows the exact message that person received — rendered subject and body, not a template. This is the answer to “what did we actually send them?”.

12.3Suppressed addresses

When a message hard-bounces or somebody marks one as spam, the provider tells the system and the address is taken out of circulation. Nothing is sent to it again until the suppression is lifted, which you can do from this panel. Temporary failures — a full mailbox, a server having a bad afternoon — do not suppress.

Lift a suppression only when you know why it happened

A complaint suppression means a real person marked TIC mail as spam. Sending to them again is how a sending domain’s reputation is lost — which costs everybody’s delivery, not just theirs.

12.4Newsletter list

The footer sign-ups, with export, and removal on request. A repeat sign-up is answered as an ordinary success, so the form cannot be used to find out who is already on the list.

The sandbox-sender banner

If the console shows a banner about sending from a sandbox address, mail is only reaching one inbox — the one that owns the provider account — and every other recipient is getting nothing. That is a configuration problem, not an operator one. Report it.

Done  Meter, log with previews, bounce and complaint feedback, suppressions, newsletter. In progress  The production sending domain — see §18.

13  Email templates

The wording of every automatic message, editable without touching a line of HTML.

13.1Blocks, not markup

Nobody should have to edit inline-styled table markup to change a sentence, so a message is composed from blocks. Each bundled template arrives as a block list you can reorder, duplicate, delete, or clear out and rebuild. A + between any two blocks opens the palette.

GroupBlocks
TextHeading · Subheading · Paragraph · Bullet list · Numbered list · Quote · Small print · Signature
EmphasisHighlight (neutral / positive / negative) · Button · Link
MediaImage · File
SpacingDivider · Spacer

Inside a text field the only markup is *bold* and [label](https://…). Everything else is written exactly as it will be read.

13.2Only show

Every block carries one visibility rule — always, when the reason is filled in, or when the reason is empty. That is what makes an optional rejection reason disappear cleanly instead of leaving an empty panel in somebody’s inbox.

13.3Variables

A template can drop in values from the record it is about — a name, a role, a reason. The editor lists the ones available to that template; the block editor writes the conditional logic for you.

13.4The controls

Subject line
Edited above the body. It takes variables too.
Preview
The message as it will arrive, rendered into the shared layout.
Send a test
Sends the current draft to an address you type. Test sends are marked in the log and hidden from it by default.
On / off
Switching a template off stops that message being sent, while still recording each attempt as blocked. Useful while a message is being rewritten.
Reset
Discards your version and puts the bundled copy back.
Images and files
Upload into a public bucket, because an email client fetches an image with no session. A file block can also tick attach it to the email as well, which sends it as a real attachment alongside the download link.
One layout, one place

Every message renders inside a shared layout template — the branding, the header, the footer. Change the layout once and every message changes with it. It is the one template still written as HTML, because it is scaffolding rather than copy.

The HTML tab is a one-way door

Saving from the HTML tab stores raw markup and the template stays hand-edited — the block editor no longer applies to it — until it is Reset. Use blocks unless you have a reason not to.

Done  Block editor, visibility rules, variables, preview, test send, on/off, reset, image and file blocks with attachments.

14  Storage

Every file the system holds, how much room is left, and which files are safe to remove.

14.1The four buckets

BucketPublicHolds
application-documentsNoPitch decks, founder CVs, financials, incorporation certificates
job-applicationsNoResumes attached to a role application
site-assetsYesImages uploaded for public pages from the content editor
email-assetsYesPictures and documents used inside an email

The two public buckets are a deliberate exception: a page’s <img> and an email client both fetch without any session, so anything shown that way has to be reachable without credentials. Only admins can put files into them.

14.2The screen

Total used, files stored, and remaining across the top; a bar per bucket marked Public or Private with its file count and size; then the object list, filterable by bucket.

Each object is marked in use or unused. “In use” means its path was found in a content section, an email template, an application record or a resume record — so a real person’s document is never mislabelled as safe to delete.

14.3Open and delete

Open
Signs a ten-minute link and opens the file in a new tab. Works for private buckets too.
Delete
Asks once. If the file is still referenced, the delete is refused and a second, blunter dialog appears saying what it would break. Delete anyway overrides it.
“Delete anyway” means what it says

The first refusal exists because something on the live site points at that file. Overriding it leaves a broken image on a public page or inside an already-delivered email. Only override when you have already removed the reference, or when you know what will break and accept it.

Why this screen exists

Files live outside the database. A database backup does not contain them, and a database record does not know whether its file is still there. This screen is the only place that reconciles the two.

Done  Usage per bucket, in-use detection across four sources, signed opens, guarded delete with an explicit override.

15  The assistant

A chat window over the console’s own data. It answers from the database, not from anything it was told in advance — and it can edit the website’s copy, with your approval.

15.1What it can reach

Console-wide counts, companies, incubation applications (including one in full), posted jobs, role applicants, users, the audit trail, site traffic, the email templates and delivery log, newsletter sign-ups, and the live copy of any section of the public site.

Useful questions: “How many startups are waiting on verification and how long has each been waiting?” · “Which role has the most applicants this month?” · “Show me what changed on the mentors page last week and who changed it.”

15.2What it can change — and what it cannot

It canIt cannot
Edit or reset a section of the website’s copy; edit or reset an email template; send a newsletter or an email to chosen recipients. Verify a company, move an application, decide an applicant, create or delete a user, delete anything at all. Those stay where they are, on their own screens, where they are attributed and audited.

The list of things it is allowed to do is the security boundary, and it is fixed in the code. No instruction typed into the chat widens it.

15.3Approving an edit

A toggle in the header sets the mode.

Review
The default. The assistant does not make the change. It shows a before-and-after card with Approve and Reject. Approving runs exactly the same operation it would have run itself, so the audit entry is identical either way.
Auto
Content and template edits happen without asking. Off by default, because these edits reach the live public site.
Auto never covers a send

Sending a newsletter or an email is always gated behind an explicit approval, in both modes. There is no setting that lets the assistant mail people on its own.

15.4Practicalities

Model
Two, chosen in the settings dialog. The default reasons before it answers — the working-out streams into a collapsed block above the reply. The second can look at an attached image.
Attachments
Attach an image and it uploads into the site-assets bucket, so you can say “put this photo on the governing body page” and approve the edit. Attach a PDF and it can ride an email. 5 MB per upload.
The key
Unless the team has a shared one configured, each admin pastes their own API key into the settings dialog. It is held in that browser only, never written to the database and never logged. Rotate it rather than treating it as permanent.
Chat history
Conversations are saved per admin. The history panel reopens or deletes your own; New chat starts a fresh one. Nobody else reads your chats.
Check what it tells you before acting on it

The reply is written from what the tools returned, and it is rendered as untrusted text on purpose. It is very good for “find me the thing” and “summarise the week”. For a decision that sends an email or changes a status, go to the screen and look.

Done  Read tools, content and template writes behind approval, gated sends, image attachments, saved conversations.

Applicant shortlistedAn admin shortlists them (§8)
Application sent to the companyAn admin marks it sent on
Not taken forwardAn admin declines them
Moving a record backwards sends nothing

Putting a company back to pending, an application back to submitted, or an applicant back to new is an internal correction — not news for the recipient. No mail goes out. This is what makes it safe to fix a mis-click.

Mail never fails your action

If the mail system is down, verifying a company or accepting an application still completes. What went wrong is recorded in the delivery log (§12). You will never be blocked from doing the work because an email could not go out.

Sign-in and password mail is separate

Confirmation emails and password-reset links are sent by the authentication provider, not through the templates above. They will not appear in the delivery log, and their wording is not editable from the console. A reset link lands on a real page that sets a new password; a link that is expired, already used, or opened in a different browser says exactly which.

17  What an admin can and cannot do

Worth reading once, so that you know which of your worries the system already handles and which it does not.

17.1Who can see what

ActorReadsWrites
VisitorPublic pages; roles from verified startupsOne role application, bot-checked and rate-limited
FounderTheir own startups, applications and applicantsTheir own records — none of it public until approved
Team memberNothing, until an admin approves themNothing, until an admin approves them
AdminEverythingEverything, and every change is audited

These limits are enforced by the database itself, not by hiding buttons. A founder cannot read another startup’s applicants by guessing a web address.

17.2Things the system guarantees

  • Every table refuses access by default; each one has explicit rules about who may read and write it.
  • The key that bypasses those rules exists only on the server. It is structurally impossible for it to reach a browser — the build fails if it is ever pulled into one.
  • Every admin write carries your identity, so the audit log names a person.
  • Private documents are only ever reachable through ten-minute signed links.
  • Public forms are bot-checked on the server, so posting straight to the endpoint does not skip the check, and rate-limited per address.
  • A second application from the same email to the same role is refused rather than duplicated.
  • Delivery feedback from the mail provider is signature-verified before it is read, and a captured request cannot be replayed.

17.3Things it does not do for you

  • It cannot undo a send. Once an email is out, it is out.
  • It cannot recover a deleted account, application or file. The dialogs ask because the answer is final.
  • It does not review what you publish. Approving a job description puts that description, as written, on a public page.
  • It does not stop an admin being reckless. Every admin has every power. Be careful who you promote in §9.
Personal data is real data

Resumes, CVs, financials and identity documents pass through this console. Do not download them to a shared machine, do not forward a signed link, and do not export a CSV to a personal drive. The export exists for handing a shortlist to the team that needs it, and for nothing else.

What a restore cannot put back from JSON

Profiles, companies, jobs and applications are keyed to authentication accounts, and an account cannot be recreated with a chosen identifier. Those tables restore only through the SQL dump. The restore script refuses to write them from JSON rather than silently orphaning records — and says so when it does. Backups contain real personal data; they are kept out of version control.

20.2Deploys

Hosted on Vercel. A push to the main branch deploys automatically. After a deploy that changes public copy, re-scrape the social preview caches and, if routes changed, resubmit the sitemap.

20.3Secrets, in one sentence each

  • The key that bypasses the database rules lives only on the server, and the build fails if it is ever pulled into a browser bundle.
  • Rotating the session secret signs every admin out immediately — which is the fast answer to a compromised session.
  • The bootstrap password stops working the moment the first admin exists.
  • The assistant’s API key is per-browser unless a shared one is configured; rotate rather than treating one as long-lived.
