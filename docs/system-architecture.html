High-level architecture

There are four layers. The browser only ever holds the publishable key, so anything it reads directly has already passed RLS. Every privileged write goes through a server route that holds the service-role key.

① Clients (browser)supabase-js with the publishable key
Anonymous visitorPublic pages, jobs, apply, newsletter

No account and no cookies beyond what's strictly necessary. hooks.server.ts logs a page view with a throwaway id and deliberately sets no tracking cookie.

Founder / team memberCookie founder_session + Supabase session

Signs in at /login and lands on /founder. Some reads and writes, such as the incubation application, applicant inbox and profile, go straight to Supabase under RLS. Anything gated by approval goes through /api/founder/*.

TIC adminCookie tic_admin_session

Signs in through the same /login page and lands on /tic-admin. Every console page is server-rendered by +page.server.ts, and every write goes through /api/tic-admin/*.

Cloudflare TurnstileBot defence

The server re-verifies the Turnstile token on /login, /apply and every role application.

ResendTransactional email + webhook

sendTemplateEmail() never throws. It skips suppressed addresses, checks the plan quota and logs every attempt to email_log. Bounces and complaints come back through /api/resend-webhook and are written to email_suppressions.

It runs a tool loop of up to 6 rounds and streams NDJSON back. It can read the whole console, but edits to content and templates and any email send need the admin's approval.

Who uses the system

There is one sign-in page, and the server assigns one of two roles: admin or founder. A team member is a founder account with a company_id and a member_status.

Visitor

Reads the public site, browses and applies for roles without an account, and subscribes to the newsletter.

Founder (owner)

Registers one or more startups, applies for incubation, posts roles, manages the team and requests changes to company details.

Team member

Added by a founder. Can use the console for that company once TIC approves them. Cannot manage the team or company details.

TIC admin

Approves or rejects everything, reviews applications, edits site content and email, manages users and uses the AI assistant.

Founders and admins use the same page. The browser never chooses its own role; the server decides which console to open.

Sign out / password reset
DELETE /api/session-login · /auth/callback → /auth/reset-password

Signing out clears both cookies and the Supabase session. A reset link goes through /auth/callback, which handles both the implicit flow and PKCE, and then forwards to the page that sets the new password.

Visitor flow

Public and anonymous. The public writes (role applications and newsletter sign-ups) go through server routes that are rate-limited, validated and, for applications, protected by Turnstile.

Browse the public site
Visitor/, /about/*, /incubation, /events, /schemes…

Copy comes from site_content, falling back to the bundled content.json, and the server renders it. Each view adds a page_views row.

Browse opportunities
/opportunities · /tic-jobs · /startup-jobs

This merges the seed posts with live jobs. RLS only shows a job when status = 'approved' and the company is verified.

Apply for a role (no account)
/opportunities/[id] → POST /api/job-applications
  • Rate limit jobApplication: 10 per hour per IP. The Turnstile token is re-verified with Cloudflare.
  • The server looks up the role itself (a seed post, or a job at a verified company), so the browser can't choose the slug.
  • Uploads the resume to the private job-applications bucket, then inserts the job_applications row.
  • If the same email applies to the same role twice, the unique index rejects it and the visitor sees 409 “already applied”.
  • The applicant is sent the job-application-received email.
Subscribe to the newsletter / unsubscribe
POST /api/newsletter · /unsubscribe

Rate-limited to 15 per hour. A repeat address still gets a plain success, so the form can't be used to find out who's on the list. The unsubscribe link in each email is signed and works with one click.

Become a founder
/apply → continues in Founder flow

Sign-up creates the account. Startups are registered later, inside the console.

Founder (user) flow

Founders can register several startups. Nothing a founder writes appears publicly until a TIC admin approves it. Every /api/founder/* call names a companyId, and requireFounder() checks that the caller owns that company or is a member of it.

Sign up
Founder/apply
  • Turnstile runs first, then supabase.auth.signUp() with metadata role:'founder'. The trigger creates the profiles row.
  • The browser calls POST /api/founder-welcome, which sends the founder-welcome email with a signed verify link. It also sends a one-time new-applicant-alert to the ops inbox.
  • Clicking the verify link hits /verify-email, which checks the signed token and sets profiles.email_verified = true.
Sign in → founder console
/login → /founder

See Sign-in. The layout loads the founder's companies, and a company switcher controls which one each page shows (PUT /api/founder/companies sets the active-company cookie).

Register a startup
/founder/companies → POST /api/founder/companiespending
  • Name, contact person, email and phone are required. A duplicate name for the same owner returns 409.
  • Inserts a companies row with status='pending', sends the company-signup receipt and adds an audit entry.
  • The company appears in the admin's Approvals → Startups queue.
Fill in the incubation application
/founder/applicationclient → Supabase (RLS)
  • An 8-step wizard with 38 questions and 4 document uploads. A draft is kept in localStorage for each user and company.
  • On submit, the browser uploads the files to application-documents and inserts the applications row directly (RLS allows it; status is not in the grant).
  • Then it calls POST /api/application-submitted, which checks ownership and sends one application-received email per application.
Post a job role
/founder/jobs → POST|PATCH|DELETE /api/founder/jobs
Company not verified403: “TIC has not verified this startup yet.”
Company verifiedCreates the job with status='pending' and adds it to the admin's Jobs queue. The apply link must use https, http or mailto.

Editing a live role sets it back to pending and clears the review note. Withdrawing a role deletes it. No email is sent; the queue itself tells TIC there's something to review.

Read applicants
/founder/applicantsclient → Supabase (RLS)

A verified company reads its own job_applications slice through a my_company_ids() policy. TIC's review_note and reviewed_at are hidden by a column grant. Founders see signed resume links and can export to CSV, but only TIC can change an applicant's status.

Add team members
/founder/users → POST|DELETE /api/founder/usersowner only

requireCompanyOwner() applies here. The server creates the auth user through the admin API with company_id set and member_status='pending'. Removing a member deletes their login too. Owners can't remove themselves. See Team member flow.

Request a change to company details
/founder/settings → POST|DELETE /api/founder/profileowner only

Founders can't write company details directly (the grant was revoked). Only the fields that actually changed are queued in company_profile_changes, and a new request replaces any pending one. The owner can withdraw a request while it's still pending.

Track outcomes & activity
/founder · /founder/activity · /founder/support

The overview shows what's live, what's queued and what came back, including rejection reasons. Activity reads audit_log, filtered to this startup's people and TIC's decisions on it.

Delete a company / close the account
DELETE /api/founder/companies · DELETE /api/account

Deleting a company also deletes its jobs (cascade). Incubation applications and applicants are kept, with the company link set to null, so TIC's records survive. Closing the account deletes the auth user and clears both cookies.

Team member flow

A team member only has access to a company after TIC approves them. A founder can't grant console access on their own.

Founderpending

The account is created with the email already confirmed and a password the founder sets. profiles.company_id is set and member_status='pending'.

TIC admin flow

Every page is server-rendered. Every write goes through requireAdmin(), which returns a service-role client tagged with the admin's id, so the audit trail names the person who made the change.

First-run bootstrap (once)
/tic-admin/login → POST /api/tic-admin-login

This only works while there are no admins. It checks TIC_ADMIN_PASSWORD with a constant-time digest comparison, creates the user and promotes it with the service role. If the admin count can't be read, bootstrap is refused, so a misconfigured key can't reopen it.

Sign in → overview
Admin/login → /tic-admin

The overview shows stat tiles and counts of what's waiting in each queue. The sign-in sends an admin-signin-alert email.

Work the approval queues
/tic-admin/approvals → PATCH /api/tic-admin/approvals

A single endpoint takes { kind: company | job | member | profile, id, decision: approve | reject, note }. See Approvals loop.

Moderate companies
/tic-admin/companies → PATCH|DELETE /api/tic-admin/companies

Verify, reject with a reason, revert to pending or delete. Verifying or rejecting emails the company (company-verified / company-rejected). Reverting to pending sends nothing. Deleting a company keeps the founder's login.

Review incubation applications
/tic-admin/applications/[id] → PATCH|DELETE /api/tic-admin/applications

Moves an application from submitted to under-review and then to accepted or rejected. Admins can add a message for the applicant and a private review note. Documents open through 10-minute signed URLs. Deleting an application removes its files first.

Process role applicants
/tic-admin/job-applications → GET|PATCH|POST|DELETE

Moves an applicant from new to shortlisted or forwarded (sent to the company), or to rejected. Each change emails the applicant. GET returns full records for the CSV export, and POST ?jobSlug= clears a closed role, deleting the resumes first.

Manage jobs & users
/tic-admin/jobs · /tic-admin/users
  • Jobs: take down any role that a company posted.
  • Users: change a role (founder ⇄ admin), suspend (ban), send a reset email, delete, or create a new admin. The last remaining admin can't be demoted, and admins can't demote themselves.
Edit site content & media
/tic-admin/content/[...key] · /tic-admin/storage

A schema-driven editor for every section, which writes to site_content (PUT to save, DELETE to reset). Images upload to site-assets. The storage console marks each object as in use or unused and returns 409 if you try to delete a file that's still referenced.

Email: templates, log, suppressions, newsletter
/tic-admin/email · /email/templates/[key]

A block-based template editor with live preview, test sends, on/off toggles and reset to the default. The page also shows the delivery log with previews, plan usage, suppressed addresses (which can be lifted) and the subscriber export.

AI assistant
/tic-admin/ai → /api/tic-admin/ai · /ai/apply · /ai/conversations
  • 21 tools. It can read all console data.
  • It can write site content and email templates. These edits need approval in Review mode and run automatically in Auto mode.
  • It can send email with send_email and send_newsletter. Sending always needs explicit approval.
  • Approving a proposal runs the same tool through /ai/apply. Chats are saved in assistant_conversations.
Audit & analytics
/tic-admin/activity

audit_log shows before and after diffs from both triggers and logAdminAction / logFounderAction calls, alongside page impressions for 7 days, 30 days or all time.

Founder ↔ admin approval loop

There are four queues. Each is filled by a founder action and cleared by an admin decision in PATCH /api/tic-admin/approvals.

1 · New startupscompanies.status

Founder: POST /api/founder/companies → pending

Admin: approve → verified · reject + reason → rejected

This is the first gate. An unverified company can't post roles.

2 · Job postingsjobs.status

Founder: post or edit → pending

Admin: approved (public) · rejected + a note the founder can read

A job is public only when it is approved and its company is verified.

3 · Team membersprofiles.member_status

Founder: POST /api/founder/users → pending

Admin: approved (the company unlocks) · rejected

4 · Company detail changescompany_profile_changes

Founder: POST /api/founder/profile → pending

Admin: approving writes the changes to companies, and a new name is copied to every posting. Rejecting leaves the company unchanged.

Founders see each decision the next time a page loads, because the layout re-reads companies on every request. The approvals endpoint sends no email. Only the Companies screen sends the verified or rejected email.

Security & guards

Several layers of protection, from the edge down to the database.

SessionsSigned cookies re-checked every request

Cookies are HMAC-SHA256 signed, httpOnly, sameSite=lax and secure in production. The signature is compared in constant time. Sessions last 30 days and slide forward on each visit. Every request calls currentAccount(), so a ban, deletion or role change applies immediately.

Route guardsrequireAdmin / requireFounder / requireCompanyOwner

A founder's companyId is never trusted. It is checked against the companies they own or belong to. “Not found” and “not yours” both return the same 403, so founders can't probe for ids.

Row Level SecurityAll 16 tables

The browser can only read what RLS allows. Status and moderation columns are left out of the grants. Ten tables have RLS turned on with no policies at all, so only the service role can reach them.

Bot & abuse controlsTurnstile + Postgres rate limits
  • jobApplication 10/h · applicationReceipt 10/h · founderWelcome 8/h
  • founderLogin 20/h · adminLogin 10/15 min · turnstile 30/10 min · newsletter 15/h
Email safetyRecipients come from the server

Endpoints that send receipts read the recipient from the stored row, not the request body, so they can't be used to email arbitrary addresses. The Resend webhook checks the Svix signature with a 5-minute window before it parses the body.

Audit trailx-actor-id → trigger

Every service-role client sends an x-actor-id header, which the audit trigger reads. Readable intent (“verified Northeast Robotics”) is logged next to each row change.

Where the README is out of dateFound while checking the code
  • The README lists /api/company-account, which doesn't exist. The real routes are /api/account (DELETE), /api/founder-*, /api/application-submitted and /api/tic-admin/approvals, and none of them are in the API table.
  • It says the admin cookie lasts 8 hours. In the code it lasts 30 days and slides forward on each visit.
  • Its diagram says hooks.server.ts sets a “visitor cookie”. The code sets no tracking cookie.
  • It says the AI assistant only writes content. It also has send_email and send_newsletter, both of which need approval.
  • It counts 14 or 15 tables. The migrations define 16, including assistant_conversations.
  • The Permissions section still describes a separate “Company” role. In the code, every non-admin account is a founder.
